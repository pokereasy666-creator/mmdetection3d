### E3 的有效性问题（执行侧发现，提交审阅）

E3 的 ΔmAP 是 −11.9 pp，是 #1 all 组增益（+1.875 pp）的 6 倍多，而且是负值，在 4 m 阈值也有 −2.7 pp 的贡献。第 8 节的保留率设计预设 E3 落在"保留了 #1 增益的多少"这一区间，即大致 0 到 1。−6.36 说明 E3 测到的主要不是这个量。数据指向以下机制：

1. **local-max NMS 的类别差异。** `transfusion_head.py:238-242` 在 nuScenes 上只对第 8 类（pedestrian）和第 9 类（traffic_cone）不做 3×3 local-max，其余 8 类按通道做 3×3 local-max。
2. **E3 中恰好只有这两类不受影响。** pedestrian 各阈值的 AP 变化为 +0.04 / +0.06 / +0.08 / +0.02 pp，traffic_cone 为 −0.14 / −0.15 / −0.06 / −0.02 pp。其余 8 类在全部四个阈值上都下降 2–30 pp，例如 car −20.7 / −17.6 / −17.3 / −15.9，bicycle −30.0 / −27.9 / −26.8 / −26.1。
3. **由此推断的机制：**
   - 注入格的 logit 为 30，注入通道取该格原始 logits 的 argmax，通常就是该目标的类别。
   - jitter 后的注入格与网络自己的峰值相距 1 格，峰值落在注入格的 3×3 窗口内，因此不再是局部最大，被 NMS 抑制。
   - 结果是网络原本放对的 query 被换成偏一格的 query，而且按 `--score orig` 拿的是偏一格处的 heatmap 分数，更低。
   - 第 8、9 类不做 NMS，网络自己的 query 保留下来，注入的只是一个低分重复框，所以几乎没有影响。
4. **E3 扰动的大多是本来就对的 query。** B0 显示，82.8% 的 GT（98140 个）在 0.5 m 内本来就有同类初始 query，而 jitter 把 8/9 的注入放在了偏离一格的位置。所以 E3 主要测的是"把已经放对的 query 挪开一格的代价"，而不是"#1 的定位增益在 ±1 格误差下还剩多少"。
5. **E3 能有效支持的结论：** 初始 query 偏离峰值一格（0.6–0.85 m），并取那一格的 heatmap 分数，代价约为 12 pp mAP，而且在各个阈值上都有。同时 mATE +27%，mAOE +24%。也就是说，单层解码器既补不回位置，也补不回分数和朝向。这说明初始位置的精度高度敏感，但它与 Q3 原定的问题（增益对精确格子的依赖）不是同一个量。

**提议（未运行；按第 2 节，新增变体须先申请）**：E3' 一对两组，用现有参数即可，不需要改代码：

```bash
# E3'-exact：只对"0.5 m 内没有同类初始 query"的 GT 注入（即 B0 的 G1 + G2 + 漏检，约 20398 个，占 17.2%），放在真值格
--oracle loc --subset missed --miss-thr 0.5 --range 0 1000 --score orig
# E3'-jitter：同一子集，±1 格
--oracle loc --subset missed --miss-thr 0.5 --range 0 1000 --score orig --jitter-cells 1 --seed 0
```

- 保留率' = ΔmAP(E3'-jitter) / ΔmAP(E3'-exact)。G0 不动，因此测的正是"把放偏的 query 修到 ±1 格内"能保住多少增益。
- E3'-exact 本身还能给出 #1 的 +1.875 pp 中有多少来自这 17.2% 的目标。
- 代价约 1.3 GPU 小时。
- 这里的 `--miss-thr 0.5` 只是用来划定 E3' 的子集，E1、E2 的漏检定义不变。
